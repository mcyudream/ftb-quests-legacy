# modern.20 物品搜索延迟修复

## 根因与修复

旧选择器每次输入都在搜索线程对全部名称调用 `PinyinSearch.key()`，共享 LRU 仅能保存 32768 个名称。更多不同中文名称按同一顺序遍历时，命中前的旧条目会被不断淘汰，导致每次查询都重新运行 ICU。中文／注册名查询也走同一条慢路径。此外，每次物品索引发布都会把整个旧快照再次送去预热，输入又先清空列表并等待 200 毫秒。

现物品索引为每个条目保留自己的检索键，后台只准备新增条目；后续查询不转拼音。未准备拼音时，中文名称／注册名仍直接匹配，准备进度自动触发当前查询刷新。搜索线程复用条目快照，背包名称与栈副本在客户端线程取得。新关键词立即取消旧查询，发布结果时核对任务、关键词和模式，取消与发布通过同一锁协调。

## 对比

在同一台 Linux x86_64 主机、Java 25、正式 **Cleanroom 0.4.0（无 alpha，非 userdev）** 上运行。数值是这些受控用例的观察结果，不是任意 Windows 整合包的延迟保证。

- 纯字符串探针使用 40000 个不同中文名称，旧版预热后中文／注册名／拼音查询仍需 **10869–11184 毫秒**。新索引准备后匹配需 **2–6 毫秒**，未准备拼音的注册名匹配 3 毫秒。该探针只测检索，不包含界面与渲染：[代码及输出](probe/)。
- 真实游戏验收 Harness 注册 40000 个带中文名的物品变体，合计 **40919** 个栈。选择器实际显示中文、全拼、注册名和 `@minecraft` 结果约 **98–101 毫秒**；搜索期间改变关键词，最终保持新查询的铁锭结果：[逐项结果](search/search-checks.json)、[客户端结果](search/result.json)。
- 为模拟拼音尚未准备，Harness 暂停后台准备队列，但不阻塞游戏线程。此时现代版本注册名查询仍在 155 毫秒显示；已发布的 modern.19 / Library modern.7 使用相同测试时超过 20 秒未显示，触发验收超时：[基线结果](baseline/result.json)。
- 初次完整准备这些人工变体的拼音仍在后台耗时约 21 秒，**未声称首次拼音索引瞬间完成**。准备期间可搜索已收集的中文名称／注册名，准备完成后的键直接复用。合成变体不代表用户实际完整整合包。

## 其他回归

- [构建记录](build.json)：Quests 89、Library 15、专服兼容补丁 2，共 **106** 项测试通过，零失败和跳过。新增测试覆盖未准备拼音时的字面匹配、共享缓存清空后仍能搜索保留键。
- [实际编辑器回归](focus/focus-checks.json)：中文／拼音搜索、焦点、章节右键、网络／磁盘读写与未知字段保留通过。新增背包拼音筛选，选中带自定义名称与 NBT 的 7 个铁锭，切换回全部模式再确认，数量与 NBT 完整。用户原任务书只复制到独立测试目录，原实例未修改。
- [专服结果](server/result.json)：未装 Ponder、Media API 或 MCP，使用正式 CR 0.4.0 专服隔离补丁，启动及任务保存重读通过，退出码 0。
- 实际运行文件的 SHA-256 见各用例的 `runtime.json`。系统输入法候选词引擎的 Windows 按键流程仍沿用 modern.19 的验收边界，本次不扩大声称范围。
